# 채용 파이프라인 보드 PRD

## 0. 문서 정보

- 제품명: 채용 파이프라인 보드
- 대상 사용자: 채용 담당자
- 제품 형태: 단일 페이지 웹 애플리케이션
- 데이터 소스: 브라우저에서 동작하는 mock API
- 구현 우선순위: Must 완성 → 핵심 테스트·접근성 → Should
- 핵심 평가 대응 원칙: 기능 단위 구현, 기능 단위 커밋, 기능 단위 AI 프롬프트·검증 기록

## 1. 제품 개요

채용 담당자가 지원자를 채용 단계별로 확인하고, 지원자 카드를 다른 단계로 이동하며 진행 상태를 관리하는 보드형 도구를 제공한다.

채용 단계는 다음 다섯 개 컬럼으로 표현한다.

1. 서류검토
2. 면접
3. 처우협의
4. 최종합격
5. 불합격

지원자 알림 등 외부 운영 상태와의 불일치를 막기 위해 일반 채용담당자 UI에서는 단방향 전이만 허용한다. 잘못된 상태 정정은 이 범위의 기능이 아니다.

## 2. 문제 정의

채용 담당자는 여러 지원자의 진행 상태를 한눈에 파악하고 신속하게 변경해야 한다. 그러나 단계 변경 요청에는 지연과 실패가 발생할 수 있으며, 화면만 바뀌고 저장되지 않거나 여러 요청이 서로의 결과를 덮어쓰면 운영 데이터에 대한 신뢰가 깨진다.

따라서 이 제품은 다음 문제를 해결해야 한다.

- 채용 단계별 지원자 현황을 빠르게 파악하기 어렵다.
- 단계 이동 시 네트워크 지연 때문에 조작이 느리게 느껴질 수 있다.
- 저장 실패 시 UI와 저장 데이터가 불일치할 수 있다.
- 지원자가 많아지면 검색·필터·스크롤 체감 성능이 저하될 수 있다.
- 마우스를 사용하기 어려운 사용자도 단계 이동과 상세 열람을 할 수 있어야 한다.

## 3. 목표

### 3.1 제품 목표

- 지원자를 단계별 컬럼에서 확인할 수 있다.
- 지원자 단계를 명시적 액션으로 이동할 수 있다.
- 이동 직후 UI가 먼저 반영되고, 저장 실패 시 정확히 원상 복구된다.
- 새로고침 후에도 성공한 이동 결과가 유지된다.
- 이름 검색과 직무 필터가 200건 이상에서 지연 없이 동작한다.
- 지원자 상세를 보드 맥락을 유지한 채 확인할 수 있다.
- 로딩, 조회 오류, 전체 빈 상태, 검색 결과 빈 상태를 구분해 표현한다.

### 3.2 제출·평가 목표

- 각 기능이 하나의 커밋과 하나의 `PROMPTS.md` 섹션으로 대응된다.
- AI 출력의 오류·누락·과설계를 실제 실행, 테스트, 코드 정독으로 검증한다.
- 설계 선택과 포기한 범위를 `DECISIONS.md`에 남긴다.
- Must 요구사항을 먼저 완성하고, Should는 독립적으로 추가하거나 미완료 사유를 기록한다.

## 4. 비목표

다음은 이번 과제 범위에 포함하지 않는다.

- 사용자 로그인, 권한, 조직 관리
- 지원자 생성·수정·삭제
- 실제 서버, 실제 데이터베이스, 다중 사용자 실시간 동기화
- 파일 첨부, 면접 일정, 이메일 발송
- 서버 페이지네이션과 복합 정렬
- 모바일 앱 수준의 완전한 반응형 UX
- 다국어 지원

## 5. 사용자와 핵심 시나리오

### 사용자

- 채용 담당자
- 한 화면에서 수백 명의 지원자를 단계별로 관리한다.
- 이름이나 직무로 특정 지원자를 빠르게 찾아야 한다.
- 잘못된 이동 또는 네트워크 실패를 즉시 인지하고 복구할 수 있어야 한다.

### 핵심 사용자 스토리

- 채용 담당자로서 단계별 지원자 수와 카드를 보고 현재 채용 진행 상황을 파악하고 싶다.
- 채용 담당자로서 지원자의 단계를 변경하고, 저장이 완료되기 전에도 빠르게 다음 업무를 진행하고 싶다.
- 채용 담당자로서 저장에 실패하면 잘못된 화면 상태가 남지 않고 실패 사실을 확인하고 싶다.
- 채용 담당자로서 이름과 직무로 지원자를 좁혀 찾고 싶다.
- 채용 담당자로서 카드에서 보이지 않는 연락처, 경력, 기술, 메모를 상세 패널에서 보고 싶다.
- 키보드 사용자로서 마우스 없이 지원자 상세 열람과 단계 이동을 수행하고 싶다.

| 이동 방식 | 드래그앤드롭 대신 명시적 단계 선택 + 이동 버튼 |

| 실패율 | GET/PATCH 요청 모두 기본 약 15%, 테스트에서는 강제 성공·실패 가능 |
| 지연 | 모든 mock API 요청에 200~800ms 랜덤 지연 |
| 자동 재시도 | 조회와 이동 모두 기본 자동 재시도 없음. 사용자가 오류를 인지하도록 명시적으로 처리 |

## 7. 채용 단계 정의

| 코드 | 표시명 | 의미 |
|---|---|---|
| `DOCUMENT_REVIEW` | 서류검토 | 지원 서류를 검토 중인 상태 |
| `INTERVIEW` | 면접 | 인터뷰 절차가 진행 중인 상태 |
| `OFFER` | 처우협의 | 채용 조건을 협의하는 상태 |
| `HIRED` | 최종합격 | 채용 절차가 합격으로 종료된 상태이며 이동할 수 없음 |
| `REJECTED` | 불합격 | 채용 절차가 불합격으로 종료된 상태이며 이동할 수 없음 |

## 8. 기능 요구사항

### FR-01. 보드·컬럼 표시 — Must

시스템은 다섯 개 채용 단계를 각각 하나의 컬럼으로 표시해야 한다.

수용 기준:

- 모든 컬럼은 단계명과 현재 표시 중인 지원자 수를 보여 준다.
- 가로 공간이 부족하면 보드 영역만 가로 스크롤된다.
- 검색·필터 결과가 적용된 수를 컬럼 카운트에 반영한다.
- 컬럼은 의미 있는 제목과 영역 구조를 가진다.

### FR-02. 지원자 카드 표시 — Must

각 지원자 카드는 다음 정보를 표시해야 한다.

- 이름
- 직무
- 지원일
- 현재 단계

수용 기준:

- 카드에 지원자 ID가 아닌 사람이 읽을 수 있는 정보를 우선 노출한다.
- 현재 단계가 카드와 컬럼에서 모순되지 않는다.
- 카드 본문을 누르거나 키보드로 실행하면 상세 보기가 열린다.
- 단계 이동 컨트롤은 카드 상세 열기 컨트롤과 중첩되지 않는다.

### FR-03. 단계 이동과 영속화 — Must

사용자는 현재 단계에서 허용된 다음 단계만 선택하고 이동 버튼을 실행할 수 있어야 한다.

수용 기준:

- 이동 요청은 `PATCH /api/applicants/:id/stage`로 전달된다.
- 이동 버튼은 지원자명·현재 단계·변경 단계를 표시한 확인 dialog를 먼저 열고, 확인할 때만 요청을 전달한다.
- 취소 button 또는 Esc는 Query cache와 mock 저장소를 변경하지 않고 이동 button으로 포커스를 복귀한다.
- 단계 선택지는 현재 단계의 허용된 다음 단계만 표시한다.
- `서류검토 → 면접/불합격`, `면접 → 처우협의/불합격`, `처우협의 → 최종합격/불합격`만 허용한다.
- 최종합격·불합격 카드에는 이동 form 대신 `종료된 단계입니다.`를 표시한다.
- 성공한 이동은 mock 저장소에 반영된다.
- 새로고침 후에도 성공한 단계가 유지된다.
- 지원자 ID 또는 단계가 유효하지 않으면 저장하지 않고 오류를 반환한다.
- 유효한 단계라도 현재 상태에서 허용되지 않은 전이는 `409 INVALID_TRANSITION`으로 저장 없이 거부한다.

### FR-04. 낙관적 업데이트와 롤백 — Must

단계 이동 시 API 완료 전에 UI를 목표 단계로 이동해야 한다.

수용 기준:

- 이동 실행 직후 카드는 목표 컬럼에 나타난다.
- API가 실패하면 해당 지원자만 이동 전 단계로 돌아간다.
- 실패한 요청은 저장소에 반영되지 않는다.
- 실패 메시지는 사용자에게 인지 가능한 형태로 표시된다.
- 다른 지원자의 동시 이동 결과를 롤백이 덮어쓰지 않는다.

### FR-05. 이름 검색과 직무 필터 — Must

사용자는 이름 일부 문자열과 직무를 조합해 지원자를 필터링할 수 있어야 한다.

수용 기준:

- 이름 검색은 앞뒤 공백을 무시한다.
- 이름 검색은 영문 대소문자를 구분하지 않는다.
- 직무 필터는 `전체`와 데이터에 존재하는 직무 옵션을 제공한다.
- 이름 검색과 직무 필터는 AND 조건으로 적용된다.
- 필터 변경이 서버 저장 데이터를 변경하지 않는다.
- 필터를 초기화하는 명시적 액션이 있다.
- 200건 이상에서도 입력이 끊기지 않는다.

### FR-06. 지원자 상세 보기 — Must

카드 본문을 실행하면 우측 상세 패널 형태의 모달을 연다.

상세 정보:

- 이름
- 직무
- 지원일
- 현재 단계
- 이메일
- 전화번호
- 경력 연차
- 주요 기술
- 메모

수용 기준:

- 패널에는 제목과 닫기 버튼이 있다.
- `Esc`로 닫을 수 있다.
- 닫은 뒤 포커스가 상세를 연 컨트롤로 돌아간다.
- 상세 패널을 열어도 현재 검색·필터·스크롤 맥락이 유지된다.

### FR-07. 로딩·오류·빈 상태 — Must

시스템은 다음 상태를 구분해 표시해야 한다.

1. 초기 로딩
2. 조회 오류
3. 전체 데이터 없음
4. 검색·필터 결과 없음

수용 기준:

- 초기 로딩은 보드 자리와 유사한 스켈레톤 또는 로딩 UI를 표시한다.
- 조회 오류에는 오류 설명과 다시 시도 버튼이 있다.
- 전체 데이터 없음과 검색 결과 없음의 문구가 다르다.
- 검색 결과 없음에는 필터 초기화 버튼이 있다.

### FR-08. 동일 카드 경쟁 상태 방지 — Should

동일 지원자에 대한 이동 요청이 처리 중일 때 추가 요청으로 데이터가 손상되지 않아야 한다.

기준 구현:

- 동일 지원자의 이동 컨트롤을 pending 동안 비활성화한다.
- 이벤트 핸들러에도 동기식 pending guard를 둬, 렌더링 전에 발생한 이중 실행을 차단한다.
- 서로 다른 지원자는 동시에 이동할 수 있다.
- 롤백은 전체 목록이 아니라 실패한 지원자 엔티티에만 적용한다.

### FR-09. 방금 한 이동 되돌리기 — Should (운영 정책상 기각)

성공한 가장 최근 이동을 일정 시간 안에 취소할 수 있어야 한다.

수용 기준:

- 원래 이동이 서버 성공한 뒤에만 `되돌리기`를 제공한다.
- 새 이동이 성공하면 기존 Undo 후보를 교체한다.
- Undo도 일반 단계 이동과 같은 API·낙관적 업데이트·롤백 규칙을 따른다.
- Undo 요청 실패 시 사용자는 실패를 인지하고, 원래 성공한 단계가 유지된다.

이번 제품에서는 지원자 알림과 같은 외부 상태가 단계 변경에 연결될 수 있으므로 Undo를 구현하지 않는다. 역방향 이동이 외부 상태와 불일치를 만들 수 있어, 상태 정정은 향후 관리자 전용 감사·정정 흐름에서 별도로 다룬다.

### FR-10. 1,000건 성능 — Should

1,000건 데이터 모드에서도 필터와 컬럼 스크롤이 부드럽게 동작해야 한다.

수용 기준:

- 검색어 변경 시 입력 자체가 목록 렌더링에 막히지 않는다.
- 필터 계산은 메모이제이션한다.
- 카드 렌더링은 필요 시 컬럼별 가상 스크롤을 적용한다.
- 1,000건 모드 실행 방법을 README에 기록한다.

### FR-11. 키보드·접근성 — Should

마우스 없이 상세 열람과 단계 이동을 수행할 수 있어야 한다.

수용 기준:

- 검색, 필터, 카드 상세 버튼, 단계 선택, 이동, 닫기, 다시 시도에 키보드로 접근할 수 있다.
- 각 인터랙티브 요소에 식별 가능한 이름이 있다.
- 단계 이동 중 상태와 성공·실패 메시지가 라이브 리전에 전달된다.
- 비활성 상태는 색상만이 아니라 속성과 텍스트 또는 상태 표시로 표현한다.

## 9. 핵심 사용자 흐름

### 9.1 최초 진입

1. 사용자가 페이지에 진입한다.
2. 로딩 UI가 표시된다.
3. `GET /api/applicants` 성공 시 지원자가 단계별로 표시된다.
4. 실패 시 오류 상태와 다시 시도 버튼이 표시된다.

### 9.2 단계 이동 성공

1. 사용자가 목표 단계를 선택한다.
2. 이동 버튼을 실행한다.
3. 지원자명·현재 단계·변경 단계를 표시한 확인 dialog가 열린다.
4. 사용자가 확인하면 카드가 즉시 목표 컬럼으로 이동한다.
5. 해당 카드의 이동 컨트롤은 처리 중 상태가 된다.
6. API 성공 시 서버 응답을 캐시에 병합한다.
7. 성공 알림을 표시한다.
8. 새로고침 후에도 목표 단계가 유지된다.

### 9.3 단계 이동 실패

1. 사용자가 이동을 실행하고 확인 dialog에서 확인한다.
2. 카드가 즉시 목표 컬럼으로 이동한다.
3. API가 실패한다.
4. 실패한 지원자만 이전 단계로 복원된다.
5. 오류 알림과 다시 시도 가능성을 안내한다.
6. 다른 지원자의 성공한 이동 상태는 유지된다.

### 9.4 검색·필터

1. 사용자가 이름을 입력하거나 직무를 선택한다.
2. 입력 컨트롤은 즉시 반응한다.
3. 검색어와 직무 조건으로 목록을 계산한다.
4. 각 컬럼의 카드와 카운트가 함께 갱신된다.
5. 결과가 없으면 검색 결과 빈 상태와 초기화 버튼을 표시한다.

### 9.5 상세 보기

1. 사용자가 카드 본문의 상세 버튼을 실행한다.
2. 우측 패널 형태의 모달이 열린다.
3. 사용자가 세부 정보를 확인한다.
4. 닫기 또는 `Esc`를 실행한다.
5. 상세를 열었던 컨트롤로 포커스가 복귀한다.

## 11. 비기능 요구사항

### 성능

- 기본 240건에서 검색·직무 필터가 체감 지연 없이 동작해야 한다.
- 기본 240건은 단순한 클라이언트 필터로 처리하고, 측정 없이 지연 렌더링이나 가상화를 선행하지 않는다.
- 1,000건 최적화는 Must 완료 뒤 실제 병목이 확인된 경우에만 별도 검토한다.

### 신뢰성

- 실패 판정 뒤에는 저장소를 변경하지 않는다.
- UI 롤백은 실패한 지원자만 복원한다.
- 새로고침 후 mock 저장소와 UI가 일치해야 한다.
- 잘못된 ID·단계 요청은 명시적 오류를 반환한다.

### 접근성

- 의미 있는 HTML 요소를 우선 사용한다.
- 모달은 제목, 닫기, 포커스 이동, `Esc` 동작을 제공한다.
- 동적 결과는 `role="status"` 또는 `role="alert"`로 전달한다.
- 중첩된 버튼 같은 유효하지 않은 인터랙션 구조를 만들지 않는다.

### 유지보수성

- 서버 상태와 UI 상태의 소유권을 구분한다.
- 필터·단계 변경 같은 핵심 로직을 순수 함수로 분리한다.
- mock API, 저장소, UI, 도메인 모델의 책임을 분리한다.
- TypeScript strict 기준으로 타입 오류 없이 빌드한다.

### AI 협업 추적성

- 구현 기능과 같은 scope 이름을 `PROMPTS.md` 제목과 커밋 메시지에 사용한다.
- 실제 사용한 주요 프롬프트 원문을 기록한다.
- 검증하지 않은 내용을 검증했다고 쓰지 않는다.
- 코드와 해당 기능의 프롬프트·리뷰 기록을 같은 커밋에 포함한다.
