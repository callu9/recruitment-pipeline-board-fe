# 채용 운영 워크스페이스 PRD

## 0. 문서 정보

- 제품명: 채용 운영 워크스페이스
- 대상 사용자: 여러 지원자와 포지션을 동시에 관리하는 채용 담당자
- 제품 형태: 단일 페이지 웹 애플리케이션
- 현재 단계: 브라우저 mock API 기반 ATS 운영 프로토타입
- 데이터 소스: MSW mock API와 `localStorage`
- 기준일: 2026-09-08
- 원본 과제: `docs/ASSIGNMENT.md`에 별도 보존

이 문서는 현재 제품 동작의 기준이다. 원본 과제의 다섯 컬럼 보드 요구사항은 구현 이력으로만 보존하며 현재 정보 구조를 제한하지 않는다.

## 1. 제품 개요

채용 담당자가 지원자, 오늘 할 일, 내부 일정, 포지션별 충원 현황을 한 작업공간에서 확인하고 지원자의 채용 단계를 변경한다.

기본 화면은 다섯 개 컬럼을 가로로 탐색하는 보드 대신 다음 네 개 업무 탭으로 구성한다.

1. `Applicants`: 지원자 검색, 필터, 단계 변경, 상세 확인
2. `Today`: 오늘 처리할 인터뷰와 후속 조치 확인
3. `Calendar`: 7일간의 인터뷰, 평가, 처우 일정 확인
4. `Positions`: 포지션별 목표와 채용 진행 현황 확인

네 화면은 동일한 지원자 Query cache를 사용한다. 한 화면에서 저장한 단계 변경은 다른 화면의 지표와 목록에도 반영된다.

## 2. 문제 정의

채용 담당자의 실제 업무는 지원자를 단계별로 분류하는 것에 그치지 않는다. 담당자는 다음 행동, 일정 누락, 평가 지연, 포지션별 충원 상태를 함께 확인해야 한다. 다섯 개 컬럼을 가로로 훑는 화면은 이 정보를 비교하기 어렵고 불필요한 시선 이동을 만든다.

제품은 다음 문제를 해결한다.

- 많은 지원자의 현재 단계와 다음 행동을 빠르게 비교하기 어렵다.
- 오늘 처리할 항목이 여러 단계와 지원자 사이에 흩어진다.
- 인터뷰, 평가, 처우 일정을 한 흐름에서 확인하기 어렵다.
- 포지션 목표와 실제 파이프라인을 연결해 보기 어렵다.
- 단계 저장 지연, 실패, 중복 입력이 화면과 저장 데이터의 불일치를 만들 수 있다.
- 종료 단계나 불합격 처리처럼 영향이 큰 결정에 추가 확인과 근거가 필요하다.

## 3. 제품 목표

- 표와 단계 탭을 사용해 지원자 정보를 짧은 시선 이동으로 비교한다.
- 담당자, 포지션, 일정 누락, 기한 초과를 조합해 필요한 지원자를 찾는다.
- 오늘 실행할 업무를 중복 없는 수치와 전체 큐로 확인한다.
- 7일간 운영 일정을 유형, 직무, 담당자로 좁혀 본다.
- 포지션별 목표 인원과 합격·진행 인원을 함께 본다.
- 현재 단계에서 가능한 다음 행동과 불합격을 명확한 버튼으로 실행한다.
- 단계 이동을 낙관적으로 반영하고 실패 시 해당 지원자만 복원한다.
- 단계 정정과 불합격 근거를 이력에 남긴다.
- 키보드와 좁은 화면에서도 핵심 흐름을 사용할 수 있게 한다.

## 4. 비목표

현재 범위에 다음 기능은 포함하지 않는다.

- 실제 ERP, 인사정보시스템 또는 급여 시스템
- 사용자 로그인, 역할별 권한, 조직 관리
- 실제 서버 데이터베이스와 다중 사용자 실시간 동기화
- 지원자 생성·편집·삭제와 파일 첨부
- 포지션 생성·편집·삭제와 승인 절차
- 일정 생성·변경·취소와 외부 캘린더 연동
- 이메일·문자·메신저 발송과 외부 알림 상태 동기화
- 평가 작성·승인과 일반 메모 작성
- 입사 온보딩, 계약, 근태, 급여, 성과 관리
- 서버 페이지네이션과 서버 검색
- Undo와 일반 사용자의 자유로운 역방향 이동

## 5. 사용자와 핵심 업무

### 5.1 사용자

- 여러 포지션을 동시에 담당하는 채용 담당자
- 지원자의 현재 상태보다 다음에 해야 할 행동을 빠르게 찾고 싶은 사용자
- 마우스 없이 주요 조회와 단계 이동을 수행해야 하는 사용자

### 5.2 핵심 업무

- 지원자 전체 현황과 단계별 인원 확인
- 이름·직무·담당자·포지션으로 지원자 검색
- 일정이 없거나 기한이 지난 지원자 확인
- 오늘 인터뷰와 작성하지 않은 평가 확인
- 주간 일정 확인
- 포지션별 충원 진행률 확인
- 다음 단계 진행 또는 불합격 처리
- 예외적인 단계 정정과 변경 이력 확인

## 6. 정보 구조와 공통 지표

### FR-01. 워크스페이스 셸과 업무 탭 — Must

시스템은 Applicants, Today, Calendar, Positions 탭을 제공해야 한다.

수용 기준:

- 현재 선택된 탭을 시각적으로 구분한다.
- 각 탭에 실제 데이터에서 계산한 항목 수를 표시한다.
- 상단에 전체 지원자, 진행 중, 오늘 인터뷰, 평가 대기, 최종합격 지표를 표시한다.
- Today 탭 수는 네 큐에 중복 등장하는 지원자를 한 번만 계산한다.
- 화면 기준일은 사용자의 local date를 사용한다.

## 7. Applicants

### FR-02. 지원자 표 — Must

지원자를 가로 컬럼 보드 대신 행 단위 표로 표시한다.

각 행은 다음 정보를 포함한다.

- 이름과 직무
- 지원일
- 현재 단계
- 담당자
- 다음 액션과 마감일
- 일정 날짜·시간·형식
- 현재 단계에서 가능한 액션

수용 기준:

- 단계 탭에서 전체 또는 한 단계를 선택할 수 있다.
- 단계 탭의 수치는 다른 필터가 적용된 결과를 반영한다.
- 행의 지원자 버튼을 실행하면 상세 패널이 열린다.
- 좁은 화면에서는 페이지 전체가 아니라 표 영역만 가로 스크롤된다.
- 지원자를 구분하는 접근성 이름에는 이름과 고유 ID를 함께 사용한다.

### FR-03. 지원자 필터 — Must

다음 필터를 조합해 지원자를 좁힐 수 있어야 한다.

- 이름 검색
- 직무
- 담당자
- 포지션
- 단계
- 일정 없음
- 기한 초과

수용 기준:

- 모든 조건은 AND로 적용한다.
- 이름 검색은 앞뒤 공백과 영문 대소문자를 무시한다.
- 필터 결과와 표시 인원 및 단계별 수치가 함께 갱신된다.
- 필터 초기화로 모든 조건을 기본값으로 되돌린다.
- 결과가 없으면 별도 빈 상태와 초기화 버튼을 표시한다.
- 포지션 조회만 실패하면 지원자 표를 유지하고 포지션 필터만 비활성화한다.

## 8. Today

### FR-04. 오늘의 운영 큐 — Must

Today 탭은 다음 네 큐를 제공해야 한다.

1. 오늘의 인터뷰
2. 평가 작성 필요
3. 기한 초과
4. 일정 미정

수용 기준:

- 각 큐의 전체 항목과 수치를 표시하며 임의 개수에서 자르지 않는다.
- 종료 단계 지원자는 운영 큐에서 제외한다.
- 같은 지원자가 여러 큐에 포함될 수 있지만 탭 수에서는 한 번만 센다.
- 각 항목에서 실제 제공되는 행동은 지원자 상세 열기이다.
- 항목을 실행하면 현재 지원자의 상세 패널이 열린다.

## 9. Calendar

### FR-05. 내부 주간 캘린더 — Must

Calendar 탭은 오늘부터 7일간의 내부 채용 일정을 표시해야 한다.

표시 대상:

- 인터뷰 일정
- 평가 마감
- 처우안 마감
- 일정이 정해지지 않은 면접 단계 지원자

수용 기준:

- local date 기준으로 오늘부터 연속된 7일을 표시한다.
- 이벤트 유형, 직무, 담당자로 필터링할 수 있다.
- 일정 이벤트나 일정 미정 지원자를 실행하면 상세 패널이 열린다.
- 종료 단계 지원자는 운영 캘린더에서 제외한다.
- 좁은 화면에서는 캘린더 영역만 가로 스크롤된다.

Calendar는 지원자 데이터에서 계산한 읽기 전용 화면이다. 일정 생성·편집이나 외부 캘린더 연동을 제공하지 않는다.

## 10. Positions

### FR-06. 포지션 현황 — Must

Positions 탭은 포지션별 채용 목표와 파이프라인 현황을 표시해야 한다.

각 행은 다음 정보를 포함한다.

- 포지션명, 부서, 직무
- 합격 인원 / 목표 인원
- 진행 중 지원자 수
- 마감일
- 채용 중, 일시 중지, 마감 상태

수용 기준:

- 수치는 현재 지원자 데이터에서 계산한다.
- 기한이 지난 마감일을 구분한다.
- `지원자 보기`를 실행하면 Applicants 탭으로 이동하고 해당 포지션 필터를 적용한다.
- 포지션 데이터는 `/api/positions`에서 조회한다.

## 11. 지원자 상세

### FR-07. 상세 패널 — Must

지원자 상세는 우측 패널 형태의 native dialog로 제공한다.

표시 정보:

- 이름, 직무, 이메일, 전화번호
- 현재 단계와 단계 액션
- 담당자, 포지션, 지원일, 다음 액션, 마감일
- 인터뷰 일정과 면접관
- 평가 상태, 점수, 담당자, 마감일
- 기본 메모와 누적 메모
- 불합격 사유와 추가 메모
- 단계 변경 타임라인

수용 기준:

- `Esc`와 닫기 버튼으로 닫을 수 있다.
- 닫은 뒤 상세를 연 버튼으로 포커스가 돌아간다.
- 상세를 열고 닫아도 현재 탭과 필터 맥락을 유지한다.
- 포지션 ID 대신 사람이 읽을 수 있는 포지션명을 표시한다.
- 데이터와 매칭되는 포지션이 없으면 `미지정`을 표시한다.

## 12. 단계 변경

### FR-08. 정상 단계 전이 — Must

채용 단계와 허용 전이는 다음과 같다.

| 현재 단계 | 기본 진행 액션 | 불합격 |
|---|---|---|
| 서류검토 | `면접 집행` → 면접 | 가능 |
| 면접 | `처우 협의` → 처우협의 | 가능 |
| 처우협의 | `최종 합격` → 최종합격 | 가능 |
| 최종합격 | 종료됨 | 불가 |
| 불합격 | 종료됨 | 불가 |

수용 기준:

- 활성 단계에는 기본 진행 액션과 `불합격` 두 선택지만 표시한다.
- 서류검토→면접과 면접→처우협의는 버튼 실행 즉시 저장을 시작한다.
- 최종합격과 불합격은 확인 dialog에서 확인한 뒤 저장한다.
- 불합격에는 사유를 필수로 받고 추가 메모를 선택적으로 받는다.
- 종료 단계에는 이동 버튼 대신 `종료됨`을 표시한다.
- 성공한 변경은 새로고침 뒤에도 유지한다.
- 일반 전이 정책에 어긋나는 직접 API 요청은 `409 INVALID_TRANSITION`으로 거부한다.

### FR-09. 예외적인 단계 정정 — Must

상세 패널은 운영상 잘못된 상태를 바로잡는 명시적 단계 정정 기능을 제공한다.

수용 기준:

- 현재 단계와 다른 단계만 선택할 수 있다.
- 항상 확인 dialog를 거친다.
- 불합격으로 정정할 때도 사유를 필수로 받는다.
- 타임라인에 이전 단계, 변경 단계, 정정 여부를 기록한다.
- 정정은 일반 단계 진행 버튼과 시각적으로 분리한다.

현재 프로토타입에는 역할별 권한이 없으므로 모든 사용자가 정정 버튼을 볼 수 있다. 실제 운영 도입 전에는 관리자 권한과 감사 주체를 정의해야 한다.

### FR-10. 낙관적 업데이트와 경쟁 상태 — Must

수용 기준:

- 요청 직후 단계, 다음 액션, 불합격 정보, 타임라인을 Query cache에 먼저 반영한다.
- mock API도 동일한 domain transform으로 최종 데이터를 저장한다.
- 저장 실패 시 실패한 지원자 한 명만 이전 엔티티로 복원한다.
- 동일 지원자의 중복 이동은 동기식 pending guard로 차단한다.
- 서로 다른 지원자는 동시에 이동할 수 있다.
- pending 동안 버튼을 비활성화하고 `aria-busy`와 저장 중 문구를 제공한다.
- 성공과 실패를 각각 `role="status"`와 `role="alert"`로 알린다.

## 13. 데이터 조회와 상태 UI

### FR-11. 로딩·오류·빈 상태와 재시도 — Must

시스템은 다음 상태를 구분해야 한다.

1. 지원자 초기 로딩
2. 지원자 조회 오류
3. 전체 지원자 없음
4. 지원자 필터 결과 없음
5. 포지션 조회 오류

수용 기준:

- 지원자 조회 오류에는 `다시 시도` 버튼을 제공한다.
- 자동 재시도는 하지 않는다.
- 사용자가 시작한 재조회는 진행 중 요청을 취소하지 않는다.
- 재조회 중에는 동기식 guard로 중복 입력을 막고 `aria-busy`를 표시한다.
- 포지션 조회 실패는 전체 지원자 화면을 막지 않는다.
- 각 빈 상태는 원인과 다음 행동에 맞는 문구를 표시한다.

## 14. 데이터 모델과 API

### 14.1 주요 엔티티

| 엔티티 | 주요 데이터 |
|---|---|
| Applicant | 기본 정보, 단계, 담당자, 포지션, 다음 액션, 마감일, 일정, 평가, 메모, 타임라인, 불합격 정보 |
| Position | 제목, 직무, 부서, 목표 인원, 마감일, 상태 |
| InterviewSchedule | 날짜, 시작·종료 시간, 화상/대면 형식, 면접관 |
| Evaluation | 유형, 작성 상태, 마감일, 평가자, 점수, 코멘트 |
| TimelineEvent | 발생일과 단계 변경 설명 |

### 14.2 API

| Method | Endpoint | 용도 |
|---|---|---|
| GET | `/api/applicants` | 지원자 전체 조회 |
| GET | `/api/positions` | 포지션 전체 조회 |
| PATCH | `/api/applicants/:id/stage` | 정상 단계 이동과 단계 정정 |

### 14.3 저장과 호환성

- TanStack Query cache를 화면의 지원자 단일 진실 공급원으로 사용한다.
- mock API는 MSW로 제공하고 성공한 변경을 `localStorage`에 저장한다.
- 모든 요청은 200–800ms 지연과 기본 약 15% 실패를 시뮬레이션한다.
- 기존 저장 데이터에는 누락된 워크스페이스 필드만 보완하고 기존 값은 유지한다.
- 기본 데이터는 240명이며 별도 저장 키를 사용하는 1,000명 성능 모드를 유지한다.

## 15. 비기능 요구사항

### 15.1 접근성

- 탭, 필터, 표, dialog, 버튼에 의미 있는 HTML과 접근성 이름을 사용한다.
- 키보드만으로 탭 이동, 필터, 상세 열기·닫기, 단계 진행, 불합격, 정정을 수행할 수 있어야 한다.
- dialog를 닫으면 실행 지점으로 포커스를 복원한다.
- 비동기 상태는 색상 외에 문구와 semantic role로 전달한다.

### 15.2 반응형 사용성

- 좁은 화면에서도 상단 탭과 주요 버튼을 실행할 수 있어야 한다.
- 정보량이 큰 표와 캘린더만 내부 가로 스크롤을 허용한다.
- 상세 dialog는 작은 화면 안에서 읽고 닫을 수 있어야 한다.

### 15.3 성능

- 기본 240명에서 검색과 복합 필터가 입력을 방해하지 않아야 한다.
- selector는 순수 함수로 유지한다.
- 1,000명 모드는 별도 실행할 수 있어야 한다.
- 가상화는 실제 병목이 확인될 때만 도입한다.

### 15.4 배포 신뢰성

- pull request와 `dev` push에서 lint, test, build를 통과해야 한다.
- GitHub Pages 배포는 `dev` push 검증이 성공한 동일 revision만 사용한다.

## 16. 주요 사용자 흐름

### 16.1 오늘 할 일에서 지원자 확인

1. 사용자가 Today 탭을 연다.
2. 네 업무 큐와 항목 수를 확인한다.
3. 항목의 `상세 보기`를 실행한다.
4. 지원자의 일정, 평가, 다음 액션과 타임라인을 확인한다.
5. 패널을 닫으면 실행한 버튼으로 포커스가 돌아간다.

### 16.2 일반 단계 진행

1. 사용자가 Applicants 행 또는 상세 패널에서 기본 진행 액션을 실행한다.
2. 서류검토→면접 또는 면접→처우협의는 즉시 낙관적으로 반영된다.
3. 처우협의→최종합격은 확인 dialog에서 확인한 뒤 반영된다.
4. 저장에 성공하면 다른 탭의 지표와 파생 목록이 갱신된다.
5. 저장에 실패하면 해당 지원자만 이전 상태로 복원되고 오류가 표시된다.

### 16.3 불합격 처리

1. 사용자가 `불합격`을 실행한다.
2. dialog에서 불합격 사유와 선택 메모를 입력한다.
3. 확인하면 단계와 불합격 정보가 함께 낙관적으로 반영된다.
4. 성공하면 타임라인에 변경이 추가되고 새로고침 후에도 유지된다.

### 16.4 포지션에서 지원자 확인

1. 사용자가 Positions 탭에서 목표와 현재 인원을 확인한다.
2. `지원자 보기`를 실행한다.
3. Applicants 탭으로 이동하며 해당 포지션 필터가 적용된다.

## 17. 현재 알려진 제한

- Calendar의 `입사` 유형 선택지는 현재 UI에 존재하지만 종료 단계 지원자를 캘린더에서 제외하므로 입사 이벤트가 생성되지 않는다. 입사 온보딩 범위를 만들기 전까지 실사용 기능으로 간주하지 않는다.
- 일정, 평가, 메모, 포지션은 조회용 seed 데이터이며 화면에서 편집할 수 없다.
- 단계 정정에는 실제 권한·감사 사용자 정보가 없다.
- 날짜는 브라우저 local date를 사용하며 조직 timezone 정책은 없다.
- 1,000명 모드에 별도 가상화를 적용하지 않았다.
- mock 저장 데이터는 브라우저와 저장 키에 종속되며 다른 사용자나 기기와 공유되지 않는다.
