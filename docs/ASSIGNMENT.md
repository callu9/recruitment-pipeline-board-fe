# Frontend 개발자 채용 과제 — AI 협업 기반 구현

## 평가 철학

“AI 없이 얼마나 빨리 짜느냐”가 아니라, AI를 도구로 삼아 요구사항을 기능 단위로 분해하고, 출력을 검증·수정하며 결과물의 품질을 책임지는 능력을 평가한다.

AI 사용은 필수다. 다만 다음을 지켜야 한다.

1. 기능별로 커밋을 분리한다.
2. 각 기능을 만들 때 사용한 프롬프트와 그에 대한 리뷰·검증을 Markdown 파일에 남긴다.
3. 진행 과정이 커밋 히스토리와 문서에서 그대로 드러나야 한다.

## 1. 배경 시나리오

채용 담당자가 지원자를 채용 단계별로 관리하는 “채용 파이프라인 보드”를 만든다.

단계:

`서류검토 → 면접 → 처우협의 → 최종합격 / 불합격`

지원자 카드를 단계 간 이동하며 관리한다. 데이터는 제공되는 mock API 또는 로컬 mock 서버를 통해 읽고 쓴다. 실제 백엔드는 없다.

## 2. 필수 요구사항 — Must

1. 보드·컬럼·카드
   - 단계별 컬럼에 지원자 카드를 표시한다.
   - 카드에는 이름, 직무, 지원일, 현재 단계를 표시한다.
2. 단계 이동
   - 드래그앤드롭 또는 명시적 액션 버튼 중 하나를 선택한다.
   - 이동은 mock API에 저장되어 새로고침 후에도 유지되어야 한다.
3. 낙관적 업데이트
   - 이동 시 UI를 먼저 반영한다.
   - API 실패 시 원상 복구하고 사용자 피드백을 제공한다.
4. 검색·필터
   - 이름 검색과 직무별 필터를 제공한다.
   - 데이터가 200건 이상이어도 체감 지연 없이 동작해야 한다.
5. 상세 보기
   - 카드 클릭 시 지원자 상세를 사이드 패널 또는 모달로 표시한다.
6. 상태 UI
   - 로딩, 오류, 빈 상태를 모두 처리한다.

## 3. 도전 요구사항 — Should

- 경쟁 상태 처리: 같은 카드를 빠르게 연속 이동했을 때 데이터가 깨지지 않아야 한다.
- 대량 데이터 성능: 1,000건 기준 스크롤·필터가 부드러워야 한다. 가상 스크롤 등을 사용할 수 있다.
- Undo: 방금 한 이동을 취소할 수 있다.
- 테스트: 낙관적 업데이트 롤백 등 핵심 로직을 테스트한다.
- 웹 접근성: 키보드만으로 단계 이동과 상세 열람이 가능해야 한다. 드래그앤드롭을 선택했다면 키보드 대체 경로가 필수다.

## 4. 기술 제약

- React, Next.js 등 스택과 상태 관리·스타일링 방식은 자유다.
- mock API는 반드시 200~800ms의 네트워크 지연과 약 15% 실패를 시뮬레이션한다.
- mock API는 자체 구현한다.
- AI 도구는 자유롭게 선택할 수 있으나 사용 내역을 문서에 남긴다.
- 외부 UI 라이브러리를 사용할 수 있다.
- 핵심 상태 로직을 통째로 대신하는 라이브러리에 의존했다면 선택 이유를 문서에 밝힌다.

## 5. 진행 방식 — 기능 단위 구현·커밋

원칙:

`기능 하나 = 커밋 하나 = 기록 한 섹션`

예시 작업 단위:

`board-layout → card-list → stage-move → optimistic-update → search-filter → detail-panel → loading-error-empty → a11y-keyboard → undo → virtualization`

### 커밋 규칙

- 커밋 하나에 기능 하나만 담는다.
- squash, force-push를 하지 않는다.
- 의미 있는 시행착오와 되돌림 흔적은 남겨도 된다.
- 메시지 형식은 `type(scope): 요약`을 사용한다.
- type은 `feat`, `fix`, `refactor`, `test`, `docs`, `chore`를 사용한다.
- 본문에는 무엇을 왜 했는지 쓴다.
- AI 초안을 어떻게 손봤는지 한 줄이라도 남기면 기록과 연결하기 좋다.

예시:

```text
feat(stage-move): 카드 단계 이동 + mock API 저장

- 드래그 대신 액션 버튼 방식 선택
- AI 초안은 로컬 상태만 갱신해 API persist가 빠져 직접 보완
```

### 못 끝낸 기능

완성보다 판단 과정을 본다. 못 끝낸 기능은 `DECISIONS.md`에 무엇을 왜 남겼는지 기록한다.

## 6. 기록

### `PROMPTS.md`

기능별로 다음을 기록한다.

```md
## [stage-move] 카드 단계 이동

### 프롬프트 1
실제 프롬프트 원문

### AI 출력 요지
AI가 무엇을 제안·생성했는지

### 리뷰 / 검증
- 무엇이 문제였는가
- 어떻게 알아챘는가
- 채택, 수정, 기각 중 무엇을 왜 선택했는가
- 수정했다면 어떻게 고쳤는가
```

평가자는 `리뷰 / 검증`을 가장 중요하게 본다.

### `DECISIONS.md`

다음을 3~5개 정도 기록한다.

- 상태 관리 방식
- 낙관적 업데이트 롤백 전략
- 폴더 구조
- 라이브러리 선택
- AI 제안 중 채택·기각한 것과 이유
- 못 끝낸 기능과 이유

## 7. 제출물

공개 GitHub Repository URL을 제출한다.

저장소 최상단 필수 파일:

- 동작하는 코드
- `README.md`
- `PROMPTS.md`
- `DECISIONS.md`

README에는 다음을 포함한다.

- 설치·실행 명령 1~2줄
- 선택한 스택
- mock API 방식
- 선택적으로 배포 링크

커밋 히스토리가 살아 있어야 한다. 단일 커밋 저장소는 크게 감점될 수 있다.

## 8. 평가 루브릭 — 100점

### AI 활용·프롬프팅 — 25점

- 요구사항을 기능 단위로 분해했는가
- 제약과 기존 코드 맥락을 잘 전달했는가
- 막힌 지점을 프롬프트로 어떻게 풀었는가

### AI 출력 검증·비판 — 25점

- `PROMPTS.md` 리뷰가 실제 검증인가
- 이해 없이 붙여넣지 않았는가
- 테스트와 리뷰로 검증했는가

### 문제 해결·설계 사고 — 25점

- 요구사항 해석이 정확한가
- `DECISIONS.md`에 트레이드오프 판단이 있는가
- 경쟁 상태, 실패 롤백, 접근성 같은 엣지케이스를 인지했는가

### 결과물 코드 품질 — 25점

- 동작 정확성
- 구조, 가독성, 일관성
- 상태·오류 처리
- 접근성
- 커밋 위생

## 9. 감점·실격 신호

- 기능별 커밋 없이 몰아서 구현하거나 히스토리를 삭제함
- `PROMPTS.md` 리뷰가 비어 있거나 형식적임
- AI 사용 흔적이 없거나 이해 없이 붙여넣은 정황이 있음
- 필수 요구사항을 충족하지 못함
- 특히 낙관적 업데이트 실패 롤백이 동작하지 않음
